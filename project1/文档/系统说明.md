# 系统说明

## 1. 系统目标与实验重点

我们需要开发一个基于 MongoDB 的简化在线问卷系统，实现注册登录、问卷创建与管理、四种题型、配置驱动的校验与跳转、问卷填写和作者统计。系统不使用关系数据库，也不采用现成问卷框架。

本次实验的重点是 MongoDB 和后端部分。因此，我们不仅需要让页面能够完成操作，还需要说明数据如何保存、集合之间如何关联、索引如何限制重复数据，以及后端如何处理权限、状态、答案校验和统计。前端使用简单的 HTML、CSS 和原生 JavaScript，主要负责收集输入和展示结果，不作为业务正确性的唯一依据。

本文件介绍系统整体结构和使用方法；数据库构建见[数据库设计](数据库设计.md)，接口参数见[API 说明](api说明.md)，后端算法和并发限制见[关键逻辑说明](关键逻辑说明.md)。

## 2. 用户角色与主要功能

系统中的作者和登录填写者使用同一套用户账号，不另外设置管理员角色。一个用户可以创建自己的问卷，也可以填写其他用户发布的问卷。

| 使用身份   | 主要功能                     | 后端限制                   |
| ------ | ------------------------ | ---------------------- |
| 未登录访问者 | 注册、登录，在设置允许时匿名填写         | 只有允许匿名且允许重复填写时，才能未登录提交 |
| 登录填写者  | 填写已发布、未关闭且未过期的问卷         | 禁止重复填写时，同一账号只能成功提交一次   |
| 问卷作者   | 创建、编辑、发布、关闭、删除自己的问卷，查看统计 | 每次管理或统计查询都需要验证作者身份     |

问卷支持单选题、多选题、文本填空题和数字填空题。作者可以配置必答、多选数量、文本长度、数字范围和整数要求，也可以根据单选、多选或数字答案配置跳转规则。文本题在首版中不支持跳转。

## 3. 架构与代码组织

根据实验要求，我们采用 Node.js + Express 单体应用，通过 MongoDB Node.js Driver 直接访问数据库。会话采用 express-session/connect-mongo，密码采用 bcryptjs；测试使用 Node 内置测试运行器和 Supertest，集成测试连接真实 MongoDB。

整体处理过程如下：

```text
浏览器页面
    -> HTTP API
    -> 请求格式检查、会话识别与 CSRF 校验
    -> 路由及业务服务
    -> 作者权限、状态、题型与跳转检查
    -> MongoDB 查询、更新、插入或聚合
    -> 统一 JSON 响应
    -> 页面展示结果
```

健康检查在业务会话中间件之前注册，直接检查数据库是否可用。页面返回 HTML 并不代表用户已获得管理权限，实际数据访问仍由后端 API 控制。

| 目录或文件                                           | 主要职责                       |

| [code/src/app.js](../code/src/app.js)           | 注册 JSON 解析、API、页面路由和统一错误处理 |
| [code/src/config.js](../code/src/config.js)     | 校验数据库地址、显式库名、端口和会话密钥       |

| [code/src/routes/](../code/src/routes/)         | 定义认证、问卷管理、公开填写和统计接口        |
| [code/src/middleware/](../code/src/middleware/) | 处理登录要求、作者查询、CSRF 和错误响应     |
| [code/src/validators/](../code/src/validators/) | 校验字段、类型、标识符、题型配置和答案        |

这种结构将 HTTP 处理、业务规则和数据库操作分开，便于说明后端逻辑，也便于第二阶段继续扩展。

## 4. MongoDB 存储方案

### 4.1 集合与关联

我们使用四个集合，不将全部数据放进一个文档。

| 集合          | 保存内容                    | 关联方式                                           |
| ----------- | ----------------------- | ---------------------------------------------- |
| `users`     | 用户名、规范化用户名、密码哈希和注册时间    | `_id` 供作者及回答记录引用                               |
| `surveys`   | 作者、问卷设置、状态、时间、题目和跳转规则   | `ownerId` 引用用户，题目和规则内嵌                         |
| `responses` | 每次独立提交、规范化答案、服务端路径和提交时间 | `surveyId` 引用问卷，`respondentId` 引用登录用户或为 `null` |
| `sessions`  | 服务端会话和过期时间              | 由 connect-mongo 管理                             |

用户、问卷和回答使用 MongoDB 的 ObjectId，题目、选项和跳转规则使用稳定 UUID。答案引用题目和选项 ID，不重复复制标题、标签或用户名。这里的引用由后端维护，不是关系数据库中的外键约束。

题目和规则通常需要整体读取和验证，因此适合嵌入 `surveys`。回答数量会持续增长，独立保存到 `responses` 可以避免所有回答挤在同一问卷文档中，受到 MongoDB 单文档 16 MiB 上限的限制。

本项目没有使用 Mongoose，也没有通过 MongoDB collection validator 完整声明字段 schema。数据结构主要通过后端白名单和校验函数保证，唯一性等约束则由数据库索引参与保证。直接绕过应用写数据库，不会自动获得全部业务校验。

### 4.2 索引与数据约束

用户名的规范化唯一索引保证大小写不同的同名账号不能重复注册。问卷作者与创建时间索引支持“我的问卷”查询；回答的问卷与提交时间、问卷与填写者索引支持统计和身份查询。

禁止重复填写时，后端额外生成字符串 `singleResponseKey`，并使用部分唯一索引限制重复记录。允许重复或匿名填写的回答省略该字段，因此不会受到这条唯一约束的影响。

`sessions` 使用 `expires` TTL 索引清理过期会话。问卷的 `deadline` 不设置 TTL，过期只影响是否允许填写，不删除问卷和历史回答。

列表和内容分页使用时间加 `_id` 排序，保证同一时间下的结果顺序稳定。不过，现有业务复合索引没有包含末尾的 `_id`，不能据此声称排序已经被索引完全覆盖，也没有通过 explain 或压力测试给出性能结论。

## 5. 主要业务流程

### 5.1 注册与登录

注册时，后端规范化用户名、校验密码并保存 bcrypt 哈希，不保存明文密码。注册成功后不会自动登录。登录成功后，系统重建会话并生成新的 CSRF token，浏览器保存会话 Cookie，服务端会话保存在 MongoDB 中。

用户名为 3～32 个 ASCII 字母、数字、下划线或连字符，去除首尾空白后按小写保证唯一。密码不去除空白，至少为 8 个 Unicode code point，实际后端还限制 UTF-8 不超过 72 字节，以适配 bcrypt。页面中的“字符”提示不代表后端已取消字节限制。

### 5.2 作者创建与管理

登录后，作者可以创建草稿，添加题目、配置校验和跳转规则，再发布已保存的问卷。发布至少需要一道题，题目和规则必须合法，截止时间如果存在，也必须在未来。

发布后，题目、跳转规则和匿名/重复参与设置被锁定，以保持历史回答的含义；作者仍可修改标题、说明和合法截止时间。关闭或过期的问卷不能重新打开。

当前页面中的发布、关闭和删除使用明确的确认弹窗。取消、按 Esc 或关闭弹窗不会执行操作，只有点击相应确认按钮才发送请求。不过，弹窗只是防止误操作的界面措施，后端仍必须独立验证作者和状态。

### 5.3 填写与保存

公开接口返回填写所需的题目、规则和状态，不返回作者引用、密码或其他用户的回答。对于已关闭或过期的问卷，公开读取仍可返回状态信息，让页面解释不能填写的原因；提交接口则拒绝继续提交。

前端逐题展示并计算下一题，返回修改时清除不再可达的旧答案。后端提交时不接受客户端路径，而是从首题独立重放，只校验实际访问的题目。被跳过的必答题不需要填写，但不能提交路径外的答案。

提交成功后，每次回答独立写入 `responses`，保存服务端确定的身份、匿名标记、路径和时间。完成页只提供通用提示，不公开回答内容。

### 5.4 作者统计

统计根据 MongoDB 中已保存的回答生成，不依赖前端累计。后端先验证作者身份，再聚合提交次数、去重登录人数、匿名提交次数、逐题访问与回答次数、选项次数和数字摘要。

总提交次数不等于总人数：同一账号允许重复填写时，每次都计入提交次数；匿名提交数也不能视为匿名人数。文本和数字明细按分页读取，不一次返回全部内容。

## 6. 运行与配置

系统需要 Node.js 20 或以上、npm 和可用的 MongoDB。以下安装、启动、seed 和测试命令均在项目根目录下的 `code/` 目录打开 PowerShell 执行。

先检查环境并安装依赖：

```powershell
node --version
npm --version
mongosh "mongodb://127.0.0.1:27017" --quiet --eval "db.adminCommand({ping:1})"
npm ci
```

服务启动时读取环境变量，也通过 dotenv 支持 `code/` 中的本地 `.env`。变量说明如下，示例结构见 [code/.env.example](../code/.env.example)。

| 变量                                   | 用途                                           |
| ------------------------------------ | -------------------------------------------- |
| `MONGODB_URI`                        | 必填，MongoDB 连接地址                              |
| `MONGODB_DB`                         | 必填，显式数据库名，不依赖 URI 默认库                        |
| `SESSION_SECRET`                     | 必填，至少 32 字符的非占位密钥                            |
| `PORT`                               | 服务端口，默认 3000                                 |
| `NODE_ENV`                           | development、test 或 production，默认 development |
| `TEST_MONGODB_URI`、`TEST_MONGODB_DB` | 集成测试连接和专用库名前缀                                |
| `SEED_PASSWORD`                      | 运行示例数据脚本时提供的演示密码                             |

下面是在当前终端配置并启动的示例，生成的密钥不会被打印：

```powershell
$env:PORT = "3000"
$env:NODE_ENV = "development"
$env:MONGODB_URI = "mongodb://127.0.0.1:27017"
$env:MONGODB_DB = "survey_system"
$bytes = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
try {
    $rng.GetBytes($bytes)
    $env:SESSION_SECRET = [Convert]::ToBase64String($bytes)
} finally {
    $rng.Dispose()
}
npm start
```

开发时可以使用 `npm run dev` 代替 `npm start`，但不能同时占用同一个端口。密钥应通过安全方式保管并复用；重新生成会影响原会话的有效性，不应提交真实 `.env`、密码、Cookie 或 token。

启动流程会连接 MongoDB、执行 ping、初始化业务索引并等待会话存储就绪，之后才开始 HTTP 监听。缺少配置、数据库不可用或索引初始化失败时，启动失败，不切换到内存存储。运行时可访问 `http://localhost:3000/api/health` 检查数据库，正常返回 `data.status=ok`，数据库不可用返回 503。

页面入口如下：

| 地址                              | 用途          |
| ------------------------------- | ----------- |
| `/register`、`/login`            | 注册和登录       |
| `/surveys`                      | 我的问卷        |
| `/surveys/:surveyId/edit`       | 编辑、发布、关闭和删除 |
| `/survey/:surveyId`             | 公开填写        |
| `/survey/:surveyId/complete`    | 完成提示        |
| `/surveys/:surveyId/statistics` | 作者统计        |

## 7. 示例数据与测试

`npm run seed` 用于插入固定演示账号和包含四种题型、跳转规则的已发布问卷。密码来自 `SEED_PASSWORD`，不是硬编码默认密码；重复运行使用 `$setOnInsert` 保留已有数据，不重置密码，不插入回答或会话，也不清库。身份冲突时脚本失败，不覆盖真实账号。具体演示身份和配置步骤见 [README](../README.md)。

集成测试使用真实 MongoDB，可以在另一个位于 `code/` 的终端运行：

```powershell
$env:TEST_MONGODB_URI = "mongodb://127.0.0.1:27017"
$env:TEST_MONGODB_DB = "survey_test_integration"
npm test
```

测试支持模块只接受 `survey_test_` 专用前缀，每次追加 UUID 创建独立库，结束时仅清理本次生成的测试库。不能将业务库或系统库用于测试清理；MongoDB 不可用时测试失败，不跳过数据库验证。

已有初版测试结果见[测试用例](../测试/测试用例.md)和[验证记录](../测试/测试结果.md)。后续确认操作修复时，完整测试达到 88/88，相关记录见 [AI 使用日志](AI使用日志.md)。这些结果来自已有执行记录，不代表生产部署或性能保证。

## 8. 当前限制与后续扩展

当前系统没有跨集合事务、在途提交与删除的补偿机制，也没有草稿版本冲突控制。MongoDB 单文档条件更新可以防止不符合状态的修改，但不能解决所有并发编辑或跨集合竞争问题。

生产模式启用 Secure Cookie，不代表已经完成 HTTPS 部署；程序当前使用 HTTP 监听，未设置 trust proxy，TLS 和代理信任需要部署时另行配置。压力测试、完整生产防护和 watch 修改热重启的实际验证也不在现有结论中。

第二阶段收到新要求后，我们会继续使用当前核心集合和稳定 ID，根据需要增加字段、索引和后端处理，并评估旧数据默认值、迁移、API 兼容及回归测试，不推倒重做。

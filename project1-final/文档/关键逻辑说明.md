# 关键逻辑说明

## 1. 数据库连接与输入检查

### 1.1 启动时先确认真实数据库可用

在 [connectDatabase](../code/src/db/connection.js) 中，程序先校验 URI 和显式数据库名，再创建 MongoClient、连接数据库、执行 `ping` 并调用 `ensureIndexes`。如果其中一步失败，关闭 client 并向上抛出错误，不使用内存对象代替业务存储。

[startServer](../code/src/server.js) 在上述步骤之后创建应用，等待 connect-mongo 会话存储初始化完成，再开始监听端口。这样可以避免 HTTP 服务已经启动，但数据库或关键索引尚不可用的情况。关闭服务时，程序停止监听并关闭会话存储和数据库连接。

### 1.2 只允许后端定义的请求字段

[basic.js](../code/src/validators/basic.js) 提供通用校验。请求必须是普通对象，字段使用白名单，并递归拒绝以 `$` 开头、包含 `.` 或涉及 `__proto__`、`constructor`、`prototype` 的键。接口不会将客户端对象直接作为 MongoDB 查询条件或更新操作。

用户、问卷和回答使用 ObjectId，外部传入值必须是 24 位十六进制字符串，再转换为 ObjectId。题目、选项和规则使用规范 UUID。布尔值必须是真正的 boolean，数字必须是真正的有限 number，不把数字字符串自动转换为数字。

全局限制为：标题及选项标签最多 200 个 Unicode code point、说明 5000、题目 100、每题选项 50、规则 500、文本答案 10000。普通字符串去除首尾空白后计数，密码不去除空白；HTTP JSON 请求体另有 100kb 上限。这些限制作用于不同层次，不能用请求体大小限制代替字段和答案校验。

## 2. 账号、会话和作者权限

### 2.1 注册与唯一用户名

[认证路由](../code/src/routes/auth.js) 将用户名去除首尾空白，校验为 3～32 个 ASCII 字母、数字、下划线或连字符，再生成小写的 `usernameNormalized`。数据库对该字段设置唯一索引，因此大小写不同的同名注册也会冲突。

密码至少为 8 个 Unicode code point，实际 UTF-8 长度不得超过 72 字节。后端调用 `bcrypt.hash(password, 12)` 保存哈希，验证时使用 `bcrypt.compare`。响应只返回用户摘要，不返回密码哈希。

注册不是“先查询是否存在，再假定插入一定成功”。即使两个请求并发注册相同规范化用户名，数据库唯一索引也只允许其中一次成功，另一请求的 `E11000` 被转换为 409 `USERNAME_TAKEN`。

### 2.2 会话与 CSRF

登录成功后，系统通过 `regenerate` 重建会话，保存用户 ID，生成新的 CSRF token，再保存会话。会话存储在 MongoDB 的 `sessions` 中，Cookie 名为 `survey.sid`，有效期设置为七天。

Cookie 使用 HttpOnly、SameSite=Lax，生产模式另启用 Secure。会话过期数据由 connect-mongo 的原生 TTL 索引清理；TTL 清理不是精确到瞬间的任务，也不用于问卷截止。

除 GET、HEAD 和 OPTIONS 外，写请求需要携带与当前会话匹配的 `X-CSRF-Token`。匿名提交和注册、登录同样需要先获取 token；登录重建会话后，客户端需要使用新的 token。退出时销毁会话并清除 Cookie。

### 2.3 在查询中同时限制问卷和作者

[getOwnedSurvey](../code/src/middleware/auth.js) 使用以下条件读取问卷：

```javascript
const survey = await db.collection('surveys').findOne({
  _id: parseObjectId(String(surveyId), 'surveyId'),
  ownerId: parseObjectId(String(userId), 'userId'),
});
```

这里的 `userId` 来自服务端识别的登录用户，而不是客户端传入的作者字段。查询同时限制 `_id` 和 `ownerId`，不能只根据问卷 ID 读取后就默认允许管理。

未登录时返回 401；已经登录但没有符合条件的资源时返回 404，不额外透露问卷是否属于其他用户。统计服务也先调用同一作者查询，再读取回答，避免只在管理页面检查权限。

## 3. MongoDB 索引与并发防重复

### 3.1 部分唯一索引的作用

[业务索引](../code/src/db/indexes.js) 中，禁止重复填写使用以下索引：

```javascript
{
  key: { singleResponseKey: 1 },
  name: 'responses_single_response_unique',
  unique: true,
  partialFilterExpression: {
    singleResponseKey: { $type: 'string' },
  },
}
```

当问卷禁止重复填写时，[submitResponse](../code/src/services/responses.js) 要求填写者登录，并生成 `singleResponseKey=surveyId:respondentId`。同一问卷、同一账号的请求会得到相同字符串，因此并发插入时也只能成功一次。

允许重复填写的记录省略该字段，而不是写入 `null`。部分索引只约束字符串字段，因此普通重复提交和允许的匿名提交可以独立保存。插入遇到与这类记录有关的 `E11000` 时，服务返回 409 `ALREADY_SUBMITTED`。

这种设计将最终唯一性放在 MongoDB 中。仅在插入前查询“是否已经回答”，不能可靠阻止两个请求同时查到“尚未回答”后都插入。

### 3.2 匿名与防重复的关系

系统不能可靠判断匿名访问者是否为同一个人，因此禁止重复填写时，即使设置允许匿名，也必须登录。允许匿名且允许重复时，未登录者可以提交，每次回答独立保存。

已经登录的用户即使填写允许匿名的问卷，也保留真实会话身份；`respondentId=null` 才对应 `anonymous=true`。匿名标记由后端生成，不接受客户端伪装。

### 3.3 索引不等于全部性能保证

作者/创建时间索引支持列表过滤，问卷/提交时间索引支持回答查询，问卷/填写者索引支持身份查询。实际分页还按 `_id` 处理时间相同的记录，但现有复合业务索引没有加入最后的 `_id`。

因此，我们可以说明索引用于哪些查询，但不能声称所有排序均被完全覆盖，也不能把尚未执行的 explain、压力测试或生产负载测试写成已有结论。

## 4. 问卷生命周期与条件更新

### 4.1 持久化状态和派生状态

[问卷服务](../code/src/services/surveys.js) 保存 `draft`、`published` 和 `closed`。`expired` 是根据状态和服务器时间实时派生的结果，不单独保存，也不使用 TTL 删除问卷。

```javascript
return survey.status === 'published' && survey.deadline !== null
  && survey.deadline <= now ? 'expired' : survey.status;
```

只有已发布且未关闭、未过期的问卷允许提交。过期派生不会覆盖 `closed`，避免关闭的问卷又显示为其他状态。

| 操作      | 后端条件与处理                                        |
| ------- | ---------------------------------------------- |
| 创建      | 建立草稿，默认禁止匿名、允许重复，题目和规则为空                       |
| 编辑结构    | 仅草稿允许修改题目、规则和参与设置                              |
| 发布      | 至少一道题，题型和规则合法，截止时间为空或在未来                       |
| 修改已发布问卷 | 仅允许标题、说明和合法截止时间，不能修改已锁定结构                      |
| 关闭      | 已发布问卷可以关闭，包括持久化仍为 published 的过期问卷；草稿不能通过关闭接口关闭 |
| 重复发布或关闭 | 有效已发布问卷的重复发布、已关闭问卷的重复关闭返回当前数据                  |
| 重新打开    | 已关闭或过期问卷不能重新发布                                 |
| 删除      | 验证作者后，先关闭，再删除关联回答和问卷                           |

### 4.2 将状态条件加入数据库更新

读取时检查状态还不够，因为请求检查后，其他请求可能已改变问卷状态。服务使用 `findOneAndUpdate`，将作者和预期状态一起放入更新条件，并通过 `$set` 写入合法字段及 `updatedAt`。

结构更新要求数据库中的 `status` 仍为 `draft`。更新已发布问卷的元数据时，还要求状态仍为 `published`，且截止时间为空或晚于检查时的服务器时间。

如果条件不再匹配，后端重新确认作者资源并返回409冲突，提示重新读取。MongoDB单文档更新是原子的，题目和规则在同一问卷文档中一起保存。当前结构更新还比较原题目和规则数组，因此不会直接覆盖另一请求已经改变的结构；基础设置与题库编辑仍无通用版本号，不能将这种结构检查视为全局版本控制。

### 4.3 发布后锁定结构

答案保存题目和选项 ID，不复制标题和标签。如果发布后随意改变题型或选项，历史回答的含义可能变化。因此，系统在发布后锁定题目、规则和参与设置，让已有回答能够继续按同一结构解释。

### 4.4 复制为草稿

复制本人问卷时为题目、选项和规则重建UUID并逐项重映射引用，保留END/数字条件，清空截止与发布/关闭时间，不复制回答；原卷不变。标题按Unicode码点截断后添加“（副本）”。

## 5. 题型配置和答案校验

### 5.1 先验证题目配置是否可满足

[normalizeQuestion](../code/src/validators/questions.js) 生成或保留稳定题目 ID，规范化标题、题型、必答、选项和校验配置。新增选项省略 ID 后由服务端生成，编辑已有选项时只能使用本题已有 ID；修改标签不改变选项 ID。

`validation` 采用整体替换，不是逐字段合并。改变 `type` 且省略 `validation` 时，配置重置为 `{}`，避免旧题型配置残留。text/number 请求禁止包含 `options`，即使是空数组也不允许；完整持久化结构仍保存 `options: []`。

| 题型       | 配置检查                                                              |
| -------- | ----------------------------------------------------------------- |
| single   | 只接受空 validation，选择题需有 1～50 个合法选项                                  |
| multiple | minSelections、maxSelections、exactSelections 必须合法，不能超过选项数量，也不能互相冲突 |
| text     | minLength、maxLength 为合法非负整数，不能超过 10000，最小值不能大于最大值                 |
| number   | min、max 为有限数，integer 为布尔值；最小值不能大于最大值，整数区间必须至少存在一个整数               |

必答多选题不能配置为只能选择零项，必答文本题不能设置最大长度为零。例如整数限制下的范围 0.1～0.9 不包含任何整数，配置阶段就应拒绝，而不是等填写时才发现无法满足。

[validateQuestions](../code/src/validators/questions.js) 还检查整个持久化数组，保证题目 ID 唯一、顺序从 1 连续、选项合法，不在验证过程中重新分配 ID 或悄悄修正顺序。

### 5.2 再验证实际答案

`validateAnswer` 根据题型处理答案：

| 题型       | 答案校验与规范化                                           |
| -------- | -------------------------------------------------- |
| single   | 必须是当前题目中的一个选项 ID                                   |
| multiple | 必须是合法选项 ID 数组，不能重复，非空时检查数量限制                       |
| text     | 必须是字符串，trim 后按 Unicode code point 计数，检查题目长度限制和全局上限 |
| number   | 必须是真正的有限 number，检查范围和整数限制；0 是合法答案                  |

未提供或为 `null` 的值统一作为空答案，多选空数组和 trim 后为空的文本也规范化为 `null`。空答案如果来自可选题，不应用非空数量或长度下限，也不触发跳转；实际访问的必答题为空则返回 422。

数字字符串、非有限数、不安全整数和非法类型不会通过校验。多选题重复选项也不会被悄悄去重后接受，而是直接拒绝。

## 6. 配置驱动跳转与后端路径重放

### 6.1 规则是数据，不是数据库中的可执行代码

[jump.js](../code/src/services/jump.js) 将允许的运算符实现为有限的函数集合，问卷中只保存规则数据。这里的“配置驱动”表示问卷可以选择条件值、优先级和目标，不代表数据库可以提交任意可执行代码。

单选支持 equals/not\_equals，多选支持 contains/not\_contains/contains\_any/contains\_all，数字支持等于、不等于、大于、大于等于、小于和小于等于。文本题在首版中没有跳转运算符。

`validateRules` 检查来源题目存在、运算符与题型匹配、判断值合法、规则 ID 在本次数组内唯一。同一来源题目的 priority 必须为非负整数且不能重复。

跳转目标只能是后续题目或 `END`，不能向前或跳到自己。这样每次跳转都会前进，避免循环。存在多条匹配规则时，较小 priority 优先；没有匹配时进入下一题，最后一题之后自然结束。

### 6.2 只接受答案，不接受客户端路径

提交请求正文只允许 `answers`。后端不接受客户端指定的 `path`、填写者、匿名标记或提交时间，也不根据前端是否显示某道题判断该题是否应校验。

`validateSubmission` 先验证问卷和规则，将答案整理为按题目 ID 索引的 Map，拒绝未知题目和重复题目，再从首题开始重放：

```text
伪代码：
验证问卷结构、规则和答案条目
current = 首题 ID
while current != END:
    取出当前题目的输入
    校验并规范化当前答案
    将当前题目加入 path
    如果答案非空，将其加入规范化 answers
    从待处理答案中移除当前题目
    根据合法答案、规则优先级和顺序计算下一题
如果还有未处理答案，拒绝路径外答案
返回规范化 answers 和服务端 path
```

`path` 包含实际访问但可选留空的题目，`answers` 只保存非空规范化答案。因此，统计可以区分“访问过但没回答”和“因跳转未访问”。

例如某规则使首题直接跳到 END，后端只要求首题符合校验，后续被跳过的必答题不需要填写；如果客户端仍提交这些题的答案，服务端会拒绝。

### 6.3 编辑结构时维护规则有效性

修改题型或删除选项时，问卷服务会清理该来源题目中失效的规则，并返回 `removedRuleIds`。删除题目时，清理将其作为来源或目标的规则，并重新生成连续顺序。

调整顺序必须提交完整、无重复的题目 ID 列表，然后重新验证全部规则。如果新顺序导致原规则向前跳转，拒绝排序，不保存不合法结构。

## 7. 提交保存与最终状态检查

[submitResponse](../code/src/services/responses.js) 的保存过程如下：

找不到问卷或问卷仍为草稿时，提交返回 404；身份不满足时返回 401；问卷关闭或过期返回 410；答案不合法返回 422；禁止重复的重复提交返回 409。

第二次读取用于缩短“先打开页面、后来关闭问卷，但还继续提交”的时间窗口，不能称为跨集合事务。最终读取之后到实际插入之间仍存在竞争窗口；当前实现不保证关闭、删除与在途插入在所有并发情况下完全原子。

正常删除先关闭问卷，再对 `responses` 执行按 surveyId 的 `deleteMany`，最后删除作者名下的问卷。这个流程没有事务或补偿机制，中途失败或在途提交竞争时不能保证全部操作一起成功。因此，使用时应先关闭并确认无人填写，再删除问卷。

## 8. MongoDB 统计聚合

### 8.1 在数据库中生成统计

[statistics.js](../code/src/services/statistics.js) 先检查作者身份，再对 `responses` 执行聚合。主要管道结构如下：

```text
$match：只读取当前问卷的回答
    -> $facet
        totals：提交总数、去重登录用户数、匿名提交数
        visited：展开 path，统计实际访问次数
        answered：展开 answers，统计非空回答及数字摘要
        options：展开选择题答案，按题目和选项统计次数
```

`totals` 先按 respondentId 分组，再合并统计。totalResponses 累加所有记录，uniqueRegisteredRespondents 只计非 null 的不同用户，anonymousResponses 累加匿名提交。因此，重复允许时同一账号多次提交会增加总数，但不会增加去重登录人数。

`visited` 通过 `$unwind: '$path'` 和 `$group` 计算访问次数；`answered` 展开规范化答案，计算回答次数。由于空答案不写入 answers，answeredCount 不包含可选留空记录。

### 8.2 选择题与数字题

选择题聚合将单选转换为单元素数组，对多选使用 `$setUnion`，再展开并按题目 ID、选项 ID 分组。提交阶段已拒绝重复选项，聚合阶段仍保证每条记录的同一选项最多计数一次。

选项比例使用 `count / answeredCount`，接口返回 fraction，而不是直接返回百分数；页面负责转换为百分比。这里的分母是该题非空有效回答数，不是整个问卷的提交次数，也不是去重人数。多选允许同时选择多个选项，因此各选项比例之和可能超过 100%。

服务端按问卷中全部选项补齐结果，零票选项也返回 count=0、ratio=0。数字摘要使用 `$isNumber` 判断有效数值，再通过 `$avg`、`$min`、`$max` 和条件求和得到均值、极值和有效数量；没有回答时，count=0，其余摘要为 null。

### 8.3 文本和数字内容分页

单题内容查询先按 surveyId 和 questionId 过滤，再按 `submittedAt:-1, _id:-1` 排序，执行 `$skip` 和 `$limit`，最后展开答案并投影出 responseId、submittedAt 和 value。

每条回答最多包含该题一次，因此先对符合条件的回答记录分页，再展开目标答案，可以与单题 answeredCount 对应。默认 pageSize 为 20，最大为 100，page 和 pageSize 必须是合法正整数。统计不一次返回全部文本内容，也不向填写者公开其他人的答案。

### 8.4 跨问卷题目统计

`library-statistics.js`复用共同版本关系，先选本人当前使用的问卷/题目实例，再以题型+有序选项标签哈希分组。跨问卷内容相同但UUID不同的选择题，以每个实例的有序options对齐票数；标签重复也按位置分别统计，不能仅按文字合并。同题改题型、改选项或选项顺序时分组，标题/必答/校验限制变化仍归同组。

摘要对关联问卷响应去重计提交（同一提交不会因题目重复而多计），respondentId跨问卷去重计登录人数；匿名计提交次数。path及answers的每次匹配均按surveyId+questionId验证。访问包括可选留空，有效非空回答只读持久化answers；数字平均对所有数值加权求avg，不平均问卷均值。单选/多选比例以各兼容组answeredCount为分母，零票0、多选比例和允许超过1。

页面卡片展开显示总计和所选组的题目指标，切换组请求其第一页，文本/数字每页20条，稳定排序含questionId以容纳同响应多个实例。查询失败清除本次结果并给重试提示，未保存题目表单不变。所有文本用既有el/textContent渲染；统计不触发保存成功提示、不修改源卷/答案，权限/非法查询由后端校验。

## 9. 确认操作与统一错误响应

### 9.1 明确确认后才发送状态变更请求

[公共前端组件](../code/public/js/common.js) 中的 `confirmAction` 返回异步布尔结果，只有明确确认按钮返回 true。取消、Esc 或关闭弹窗返回 false；删除通过 `confirmDeletion` 复用该组件。

列表和编辑页等待确认后才发送删除、发布或关闭请求，并使用忙碌标记避免重复点击。取消放弃未保存修改时，也停止后续操作。相关测试位于 [deletion-ui.test.js](../code/tests/deletion-ui.test.js)。

这部分用于修复误操作问题，但不是后端授权机制。直接调用接口仍需要通过会话、CSRF、作者身份和状态检查。

### 9.2 后端统一返回错误

[errors.js](../code/src/middleware/errors.js) 使用 `HttpError` 和统一错误处理器。成功响应为 `{data: ...}`，失败响应为 `{error: {code, message, details?}}`。

| HTTP 状态   | 主要含义                    |
| --------- | ----------------------- |
| 400       | 字段、配置、ID 或 JSON 不合法     |
| 401       | 未登录、登录失败或不满足参与身份要求      |
| 403       | CSRF token 不合法          |
| 404       | 资源不存在、草稿不可公开访问，或作者查询不匹配 |
| 409       | 状态冲突、用户名重复或禁止重复的回答冲突    |
| 410       | 提交时问卷已关闭或过期             |
| 413 / 415 | 请求体过大或编码不支持             |
| 422       | 答案、必答或提交路径不合法           |
| 500 / 503 | 内部错误或明确的数据库不可用          |

已知业务错误可以返回字段或题目 ID，便于定位输入问题。内部错误不返回原始数据库异常、堆栈或密钥；启动失败也不直接打印可能包含连接凭据的驱动错误。

### 9.3 保存结果反馈

保存类操作统一显示“保存成功”或“保存失败，请再试一次”，取消确认不误报；普通查询/分享/关闭保留对应提示。操作锁防重复请求，失败释放交互状态。

## 10. 个人题库、内容去重和复用

去重修复：`questionContentKey`对规范化题目计算SHA-256，按内容比较而非UUID或标题单独比较。选项顺序参与，省略/显式默认校验值归一；`create`使用`ownerId + contentKey`过滤及`$setOnInsert`，已存在则直接返回原记录，保持原ID与时间。唯一索引兜底处理并发，相同内容的重复创建及从问卷保存继续成功，不产生新记录。更新时同时刷新指纹，若撞上本人已有相同内容，则在原内容未被并发改写的前提下删除冗余模板并返回已有项；否则409。每个用户单独去重，问卷独立副本不参与题库清理。

连接初始化在HTTP监听前迁移历史题库：保留每组最小ObjectId记录，补指纹、移除相同内容的冗余项后建唯一索引；已有索引时跳过。迁移不更改问卷、回答、保留题目的UUID与时间，不是跨进程在线迁移机制，第一次更新应停掉旧版写入进程再重启。

`createQuestionLibraryService`将个人常用题保存在独立的`questionLibrary`集合。创建和编辑复用`normalizeQuestion`，因此题型、选项、必答及校验条件与问卷一致。用户身份由会话确定，模板按`_id + ownerId`查找，目标问卷通过`getOwnedSurvey`验证，不能仅凭知道模板或问卷ID越权访问。

从问卷保存时只读取服务器已保存的题目，并通过`questionInput`白名单提取标题、题型、必答、选项标签和校验条件。移除原题目ID、选项ID和顺序后规范化，生成独立模板，不复制跳转规则、问卷状态、回答或用户数据。前端按钮不重载编辑表单，未保存内容仍保留，提示明确说明存入的是已保存版本。

从题库选用时先读取本人模板，再复用问卷`addQuestion`执行目标作者、草稿、数量上限检查。新题目和选项重新生成UUID，按末尾顺序嵌入目标问卷；不同问卷、同一问卷多次选用的题目相互独立。复用采用快照而非共享可变引用，模板删除或编辑不会反向更新问卷，更不会改变历史回答。来源删除与选用同时发生时，若选用已读取合法定义，可完成该份快照；不承诺跨集合事务。

结构保存`saveStructure`比较`status=draft`、原`questions`、原`jumpRules`和原`questionHistories`；规则替换比较草稿状态、题目和规则。一旦另一请求已更改对应结构，更新匹配失败并返回409，调用方重新读取后重试。题库编辑也比较原题目和本地历史；显示版本号不作为全局并发锁，跨集合操作仍有一致性边界。

题库管理页与问卷编辑页通过独立的`window.SurveyQuestionFields`共享题目输入组件。`window.SurveyApp`被冻结，组件不向其中动态写入属性。题库管理页每页5题，选题菜单按API页读完全部条目并显示5行滚动列表；导入前沿用未保存修改确认，取消不发送导入请求；题库删除必须明确确认。导入后的填写、跳转和本卷统计沿用原接口与数据格式。

## 11. 版本谱系、并存与恢复

`shared-question-history.js`按会话owner汇总实时题库、问卷本地历史和questionVersionSources归档。并查集按来源题目和共享版本ID划分关联分量，去除原样导入/复制的初始版本别名，保留内容变化和恢复节点，再按父节点优先及时间/UUID确定显示序号。本处head映射为共享版本ID，所以关联位置看到相同版本列表，各自“当前”仍不同。来源中的显示版本号按versionId重新解析，避免从旧局部历史升级后显示错位。

“创建新版本”提交`POST /api/question-library/:id/versions`，先验证来源属于本人并且versionId在共同历史内，将选定快照作为默认配置规范化输入后创建独立题库条目。原样保存或与已有同内容项相同则按原唯一索引复用，仍成功且记录来源；内容不同则新建，父节点指向被选择的版本。题库历史弹窗可从任意旧节点派生，取消/关闭不写入。

问卷选题支持额外versionId，服务器读取该条目共享历史中的指定版本，复制配置并生成新题目/选项UUID。版本选择只改变导入来源，不恢复源题；未传版本仍选用题库条目当前内容。问卷修改后追加本地版本并归档，共享读取立即包含这一分支；反向的题库修改同理。问卷复制继承来源关系，各分支不自动切换内容；发布锁仍由后端验证。

旧题没有来源时只按初始快照与本人题库版本完全一致建立后备关联；保存后将推导来源固化到历史。不同用户分享不传私人题目/版本ID，所以不能读取或加入分享者谱系。完整内容不同且无来源的旧题不按标题猜测。

归档在成功结构更新后和删除前执行，幂等追加；读视图合并实时数据及归档，归档故障不会静默隐藏已成功写入的实时版本。跨文档非事务、显示序号可能在历史汇合时重排、查询规模及容量边界见数据库设计。

恢复校验UUID属于本人当前共同谱系，保持本处题目ID/题序，使用旧配置并追加新版本。问卷仅draft可恢复；改变题型或移除旧选项时清理失效源题规则，再验证全结构。恢复不重建曾删除的规则。未保存表单必须明确确认放弃，失败保留弹窗重试；已发布卷前后端均拒绝恢复。

## 12. 分享、通知与计数

题库服务提供`shareFromLibrary`与`shareFromSurvey`，前者按`_id+ownerId`查询，后者通过问卷作者与题目UUID查找。请求只能提交接收者username，不能伪造源题或senderId。接收者必须是另一位已注册用户。后端通过`questionInput/normalizeQuestion`产生快照，保留四题型配置，移除源UUID/题序，不复制问卷规则、答案及身份权限；只向通知集合upsert，不写接收者题库。同发送者、接收者、内容重复分享复用通知，不改变已有处理状态。

通知列表及接收/删除均以会话用户的recipientId过滤。接收通过`findOneAndUpdate`对pending或租约过期的accepting项取得处理权，生成operationId与30秒leaseUntil；再调用接收者题库create去重，按同operationId更新accepted及时间，移除短期令牌。失败则按同令牌恢复pending；进程异常未恢复时过期后可刷新重试。多请求可能返回200或409，题库唯一索引保证同内容不重复；accepted重试仅确认完成状态。

删除仅匹配pending/accepted，accepting返回409，避免未完成接受过程被正常删除。删除待处理通知不新增题库，删除已接受通知仅清理历史；分享者原题、问卷副本与回答不受影响。操作不跨集合事务，题库写成功但通知更新失败时可能暂时出现状态滞后，通过再次接收去重恢复，不宣称强原子性。

前端两个入口共用`shareQuestion`模态框，提供用户名、确认与取消；取消/关闭/Esc不发送请求，请求中锁定输入和提交避免重复触发。失败留在弹窗中可修正用户名并重试；成功提示到通知中确认。接收者通知页提供完整题目预览、每页5条、加入/删除与确认删除，加入沿用“保存成功/失败”反馈，不会自动修改问卷。

计数按recipientId及pending/accepting查询；前端递增请求序号防旧响应覆盖新数字，0隐藏，401隐藏并停轮询，网络失败不覆盖原操作反馈。可见页面15秒轮询，进入、聚焦、恢复可见与通知操作后主动刷新，匿名不请求私人数量。

## 13. 题目使用关系查询

题库服务usages先按条目ID/owner验证资源，再用sharedHistoryReader得到关联题目UUID集合。查询同owner且当前questions包含关联UUID的问卷，稳定排序分页；对结果中的每个匹配题读取共同历史head，返回其实际所用versionId/显示版本。每份问卷只占一条结果，多次使用保留多个questions条目。已移除题目虽仍有归档，不在当前questions中，故不列出。

前端题库卡片内展开只读结果，每页5份，提供链接、状态、题序、标题/版本及收起。复用action的操作锁防止重复请求，查找失败保留重试说明，再点击从第一页重查；保留上方dirty表单。显示文字均通过textContent及既有el/link构造，不能将题目或问卷标题解释为HTML。评估后可使用原有“创建新版本”进入预填表单，不会自动修改现有问卷。

## 14. 验证与一致性边界

核心逻辑由Node测试、Supertest和真实MongoDB验证，组件测试使用VM/简化DOM，可选Chrome脚本验证真实交互。完整143项通过及浏览器证据见[测试结果](../测试/测试结果.md)。版本归档、通知接受和删除非跨集合事务，历史容量及课程规模查询限制见[数据库设计](数据库设计.md)。

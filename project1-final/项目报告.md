## 1. 项目目标与范围

我们需要开发一个基于 MongoDB 的简化在线问卷系统，包含以下功能：注册登录、四种题型、配置驱动的校验与跳转、问卷填写和统计、个人常用题库、题目分享与通知、不同版本并存与恢复、题目使用关系查询，以及跨问卷的单题统计。在实现过程中，我们不使用关系数据库，也不采用现成的问卷框架。

本项目的重点是 MongoDB 数据建模、权限控制、索引、并发处理，以及数据含义的一致性。前端部分使用原生 HTML、CSS 和 JavaScript，主要负责输入和展示。交付时，我们将代码、设计说明和测试资料分别放在 code/、文档/ 和测试/ 中。

## 2. 架构与工程设计

在架构部分，我选择了 Node.js + Express 单体应用，并按路由、中间件、业务服务、校验和数据库模块进行分工。数据库使用 MongoDB 原生驱动，会话部分使用 express-session/connect-mongo，密码部分使用 bcryptjs。程序启动时，先校验配置，再连接数据库、执行 ping 并建立索引；如果这些步骤失败，程序会退出。关闭程序时，则释放 HTTP 服务、会话存储和数据库连接。

在前后端分工上，前端负责收集输入和展示结果，后端独立验证作者身份、问卷状态、题型、答案和填写路径。测试部分采用 Node 内置测试运行器和 Supertest，集成测试连接真实 MongoDB，另外使用 Chrome 进行实际操作验收。更详细的结构说明见[系统说明](文档/系统说明.md)。

## 3. MongoDB设计

| 集合                   | 设计用途                            |
| ---------------------- | ----------------------------------- |
| users                  | 规范化用户名、哈希密码与账户        |
| surveys                | 作者、生命周期、题目/规则及本地版本 |
| responses              | 独立响应、身份、答案及访问路径      |
| sessions               | 持久化会话及TTL                     |
| questionLibrary        | 个人复用定义、内容指纹及本处head    |
| notifications          | 分享快照、收件人、状态及接受租约    |
| questionVersionSources | 同用户题目版本与来源归档            |

在数据库设计中，我们将通常需要整体读取的题目和规则嵌入问卷，而把不断增加的回答独立保存，避免所有回答集中在单个问卷文档中。文档使用 ObjectId 定位，题目、选项、规则和版本则使用稳定的 UUID。用户名唯一、禁止重复提交、同一用户的相同题目去重，以及版本归档的唯一性，都由相应的唯一索引参与保证。会话通过 TTL 清理过期记录，但问卷到期不会因此被删除。详细字段、索引和容量限制见[数据库设计](文档/数据库设计.md)。

## 4. 问卷、题型、校验与跳转

在问卷管理部分，作者可以先创建草稿，逐题保存内容并配置规则，再发布问卷。发布后，我们锁定题目、规则和参与设置，避免后续修改改变已有回答的含义；标题、说明和合法的截止时间仍可调整，关闭或过期的问卷则不能重新打开。复制问卷时，系统会生成独立的 draft，重新映射 ID 和规则引用，清空截止时间及发布时间，不复制原有回答。

根据题目类型，我们使用 single、multiple、text 和 number 分别表示单选、多选、文本填空和数字填空，并支持必答、多选数量、文本长度、数字范围及整数限制。后端先检查配置是否能够满足，再校验实际答案。文本经过 trim 后按 Unicode 码点计数，数字必须是 JSON 数值，其中 0 是有效答案。非选择题的请求不允许包含 options；validation 采用整体替换方式，变更题型时可以重置配置。

在跳转部分，我们把规则作为数据保存，不在数据库中存放可执行代码。规则只支持白名单中的运算符，目标只能是后续题目或 END；同一来源题目的优先级必须唯一，数值较小的规则优先匹配。填写者返回修改时，前端会清除不再可达的答案，后端也会独立重放路径，拒绝未知、重复或路径外的答案，被跳过的必答题无需填写。删除题目或改变题型时，系统会清理失效规则；如果排序造成非法的向前跳转，则拒绝该操作。

## 5. 题库复用、版本与协作

在个人题库部分，我们实现了题目的创建、查看、编辑和删除，也允许把问卷中已经保存的题目加入题库。系统按完整内容指纹去重，并通过并发 upsert 处理重复保存：操作仍然成功，但相同内容只保留一份；标题相同、配置不同的题目可以同时存在。题库列表每页显示 5 题，问卷编辑页进入时自动读取题库，选题菜单最多显示 5 行，并支持滚动和键盘操作。选用题目时，系统重新生成题目和选项 UUID，不复制规则或回答。

为了让不同版本可以同时使用，我们提供了“创建新版本”功能。用户可以基于当前内容或任意历史快照创建独立条目，同时保留旧条目；问卷也可以指定历史版本进行导入。同一用户的题库、问卷和问卷副本通过来源关系共享历史，但各处的 head，也就是当前版本指向，以及实际内容仍然独立。恢复旧版会追加一个节点，只修改当前操作的位置；已发布问卷只能查看历史。如果页面还有未保存的表单内容，用户需要明确选择放弃后才能恢复。版本以 UUID 作为稳定身份，显示用的 v 序号可能在历史合并后重新排列。

在历史保留方面，我们通过归档，使源条目删除后仍能从其他关联位置查看已经保存的版本。对于缺少来源的旧题，只根据初始完整内容匹配本人题库，不单凭标题建立联系，也不追溯从未记录的修改。分享题目时，系统只把独立快照发送到对方的通知中，由对方决定加入题库还是删除，不授予源问卷权限，也不共享私人历史。通知角标显示待处理数量，为 0 时隐藏，并通过轮询和操作后的刷新更新。

为了方便了解题目的使用范围，我们增加了“查找对应问卷”。它会列出本人当前使用该题目及其关联版本的问卷，每页显示 5 份，并提供状态、题目位置、所用版本和跳转入口。已经删除的问卷或已移除的题目不会继续显示，用户可以根据查询结果决定直接编辑，还是创建新版本。

## 6. 提交、统计与安全口径

在参与设置上，只有同时允许匿名和重复填写时，用户才能未登录提交；禁止重复填写时必须登录，并由 partial unique 索引处理并发冲突。填写者身份来自会话，提交时间由服务器生成，不能由客户端自行声明。保存前，后端会再次检查问卷状态，已关闭或过期的问卷拒绝写入；完成页也不会公开答案或填写者身份。

在本卷统计中，我们区分提交次数、去重后的登录人数、匿名提交次数，以及题目访问次数和有效非空回答数。选择题以有效回答数为分母计算比例，多选题各项比例之和可以超过 100%；数字题提供 count、平均值和极值，文本与数字的填写内容则分页展示。数字题没有回答时，均值和极值为 null，选择题中零票的选项仍然显示。

跨卷统计只查询本人当前关联的题目实例。我们将题型相同、选项标签及顺序相同的题目合并，按选项位置映射不同的 UUID；题型或选项不同的版本分组处理。数字平均值根据原始回答加权计算，不直接平均各问卷的均值。同一问卷多次使用该题时分别计回答，同一人的重复回答保留，但登录人数跨问卷去重。摘要按关联问卷的提交计数，也包含跳过该题的提交；填写内容附带来源和时间，查询本身不修改问卷或回答。

在认证和安全部分，注册成功后不会自动登录，登录时更新会话和 CSRF，退出时销毁会话。所有私人资源按 owner 或 recipient 过滤，写请求需要携带 CSRF，并拒绝危险键和未知字段。页面把回答作为纯文本展示，内部错误不会向用户泄露堆栈或凭据。

## 8. 第二阶段的变化情况说明

### 8.1 第一阶段的设计

在第一阶段，我们主要围绕单份问卷的创建、填写和统计进行设计，采用 Node.js、Express 和 MongoDB 原生驱动，并按路由、中间件、业务服务和校验模块分层。数据库使用 users、surveys、responses 和 sessions 四个集合：题目与跳转规则嵌入 surveys，回答独立保存在 responses 中，通过稳定的题目和选项 UUID 对应答案。

当时，题目主要属于具体问卷，我们还没有建立独立的个人题库，也没有记录可追踪的版本来源和跨问卷使用关系。统计以 surveyId 为范围，主要用于查看单份问卷的结果。为了保护已有回答的含义，我们在发布后冻结题目、规则和参与设置，这一约束在第二阶段仍然保留。

### 8.2 新需求带来的问题

进入第二阶段后，我们需要支持保存常用题目、分享给他人、复制问卷、记录和恢复旧版本、保留不同版本，以及查询题目的使用范围和跨问卷统计。面对这些要求，题目不能只作为某份问卷内部的一段配置，还需要能够重复使用，并记录来源和版本之间的关系。

在考虑实现方式时，我们发现，如果让所有问卷直接引用同一份可变题目，编辑题库就可能改变已发布问卷，使历史答案与选项含义对不上；但如果只复制题目、不记录来源，又无法知道副本来自哪一版，以及被哪些问卷使用。不同问卷的选项 UUID 也不相同，不能简单按 UUID 相加统计；题型或选项变化后，直接合并还会混淆不同含义的回答。此外，重复保存、并发接受分享和并发修改，也可能带来重复条目或版本丢失的问题。

### 8.3 为什么需要修改原设计

原有设计能够保证单份问卷的数据完整，但还缺少跨问卷复用和追踪的能力。因此，我们需要保留问卷的独立快照，同时把“可复用题目定义”“当前使用的内容”和“共同版本历史”分开管理。具体来说，题库提供选题入口，各问卷保存自己实际使用的内容，再通过来源关系连接历史、查询使用范围并汇总统计。

通过这样的调整，我们可以在复用题目的同时保留各问卷的独立性。题库和问卷中的修改会进入共同历史，但不会自动替换其他位置正在使用的内容；已发布问卷仍然只读，需要改题时，可以复制为草稿，或在其他草稿中选用新版本。分享题目也采用独立快照，由接收者明确决定是否加入，避免直接修改他人的题库或开放私人问卷。

### 8.5 数据结构如何变化

在数据结构方面，我们将数据库从四个集合扩展为七个集合，并通过附加字段和独立集合实现新功能，同时保持原有问卷和回答结构能够继续读取。各部分的变化如下。

| 数据位置                  | 原结构或用途            | 调整后的结构与作用                                                                                         |
| ------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------- |
| questionLibrary           | 无独立题库集合          | 保存ownerId、question、contentKey、questionHistory及时间字段，提供复用定义和本处当前版本                   |
| notifications             | 无题目分享通知          | 保存发送者/接收者、题目快照、来源及pending/accepting/accepted状态，使用operationId和leaseUntil控制接受过程 |
| questionVersionSources    | 无共同版本归档          | 按ownerId/questionId归档版本及来源，支持关联历史与删除源条目后的版本保留                                   |
| surveys.questionHistories | 无逐题历史数组          | 保存questionId对应的本地历史，记录headVersionId、origin和版本快照                                          |
| Version                   | 无历史版本实体          | 包含版本UUID、父版本、依据版本、恢复来源、题目快照和保存时间；显示序号用于展示，UUID用于稳定定位           |
| responses                 | 按问卷保存answers和path | 保留原格式，继续使用问卷内题目/选项ID，统计时再通过来源关系映射，不重写历史答案                            |

配合这些变化，我们还增加了题库作者与内容的唯一索引、通知接收者与状态索引、分享内容唯一索引，以及版本归档的 ownerId/questionId 唯一索引。在判断题目是否重复时，完整内容指纹会忽略题目和选项 UUID、题序，比较规范化后的标题、题型、必答、选项顺序和填写限制，从而区分真正重复的题目与标题相同但内容不同的题目。

### 8.6 程序如何调整

在后端调整中，我们继续沿用原有认证、作者权限、题型校验和错误响应，增加题库、通知、本地历史、共同历史及跨卷统计服务，再通过相应路由提供接口。创建、编辑和导入题目时，仍然复用题目规范化函数；修改结构时比较原有题目、规则和历史，如果发生并发竞争，就返回 409，避免后一次修改直接覆盖已经保存的内容。

复制问卷时，我们为题目、选项和规则生成新的 UUID，并重新映射规则中的来源、目标和选项值，END 和数字条件保持原来的含义。新问卷始终为 draft，截止时间以及发布、关闭时间都会清空。恢复旧版时，则保留当前位置的题目 ID 和顺序，追加一个新版本，必要时清理失效规则，不覆盖旧版本，也不重建已经删除的规则。

对于共同历史，我们通过读取器汇总同一用户的题库、问卷和版本归档，利用来源题目及版本 ID 连接版本关系，并处理原样导入产生的初始快照别名。使用查询只检查当前仍存在的问卷题目；跨卷统计则先确定题目实例，再按题型和有序选项标签分组，将独立的选项 UUID 映射到组内位置。数字统计直接对全部原始回答求平均，而不能平均各问卷已经算出的均值。

在前端部分，我们增加了题库操作、版本查看、恢复与派生、通知处理、使用查询和跨卷统计入口，同时保留未保存修改确认和操作锁。查询不会修改题目，分享不会发送尚未保存的表单内容，回答也继续按纯文本展示。

### 8.7 兼容性问题与处理

在兼容性方面，我们主要遇到了以下问题：旧题缺少内容指纹和来源，独立副本的 UUID 不同，重复条目合并后 ID 可能变化，以及旧版显示序号与共同历史序号不一致。处理这些问题时，我们保留原问卷和 responses 格式，通过附加字段、启动时的索引初始化，以及读取时的兼容逻辑接入新功能。

首次建立题库内容唯一索引前，系统按作者和完整内容整理重复模板，保留 ObjectId 最小的记录及其 UUID 和时间，不修改问卷快照或回答。对于没有历史的旧记录，我们以现存内容建立基线；没有来源时，只有初始完整内容与本人题库某个版本一致，才建立关联，不能只凭标题猜测，也不能找回从未记录的修改。

模板合并后，接口可能返回不同的条目 ID，因此前端需要重新读取最新列表。版本操作始终提交 UUID，不把可能重新排列的 v 序号作为外键；来源展示号也根据稳定的 versionId 重新解析。对于不同题型或选项的版本，我们分组统计，不为了汇总而修改历史选项 ID；分享双方之间也不连接私人历史。通过这些处理，新功能不要求清库或重新生成已有问卷。

### 8.8 如何保证旧功能仍然可用

首先，我们保留了原有身份验证、参与限制、题型与答案校验、路径重放、发布锁和回答存储格式，使选入的题目仍然能够通过原来的填写和本卷统计流程。新增接口继续复用这些校验，避免另建一套互不一致的规则；新增关系和统计读取也限定在本人资源范围内。

其次，我们通过回归测试检查原有行为是否仍然正常。完整自动化测试共 143 项，全部通过，其中原有的认证、会话、问卷管理、跳转、提交、防重复、本卷统计、HTTP 重启和 seed 幂等测试继续保留。新增测试则检查复制前后原卷和回答不变、题库编辑不影响已选快照、恢复不覆盖旧历史，以及旧数据关联、选项映射和跨卷统计。Chrome 也同时验证原有保存、取消确认、填写相关复用流程，以及新增的题库、通知、版本和查询操作，两个账号都没有出现页面异常。

对于兼容性的结论，我们仍以实际覆盖的场景为范围。通知接受、题库合并、归档和删除没有采用跨集合事务，历史文档也仍受 16MiB 限制；功能扩展并不代表这些限制已经消失，具体说明见下一节。

## 9. 问题处理与限制

| 问题                    | 处理方式                         | 边界                        |
| ----------------------- | -------------------------------- | --------------------------- |
| Windows测试通配符不展开 | 使用node --test tests            | 命令在code/执行             |
| 取消确认仍执行操作      | 明确批准才写入，操作锁防重入     | 后端仍独立校验              |
| 匿名不能可靠防重复      | 防重复时要求登录及唯一索引       | 匿名次数不是人数            |
| 改题破坏旧回答含义      | 发布冻结、复制草稿、独立快照     | 新版本不自动替换原内容      |
| 重复题与版本关系丢失    | 内容唯一索引、分支合并及来源归档 | 非多文档事务                |
| 问卷均值不等于总体均值  | 跨卷按原始数值求avg              | 不同题型/选项分组           |
| 删除与在途提交竞争      | 先关闭并正常级联清理             | 无跨集合原子保证            |
| 历史与查询规模增长      | 归档、按用户汇总及分页           | 16MiB限制，未给压力性能保证 |

对于仍然存在的限制，我们保留了明确说明：通知接受、版本归档和题库合并失败时，不能保证所有写入都回滚；统计中的多次聚合也不属于事务快照。目前还没有验证跨浏览器兼容、灾难恢复或生产环境 HTTPS，启用 Secure Cookie 也不能代替 TLS 和代理配置。

## 10. AI 使用说明

在 AI 使用部分，我主要负责提出需求、反馈工程方案、检查使用效果并提出调整要求；AI 负责辅助梳理业务、生成或修改代码、补充测试和整理文档。提出修改要求与亲自编写代码是不同的工作，记录中分别说明。

根据实际开发过程，AI 的帮助、出现的问题和我负责的部分如下：

- AI 帮了什么：帮助梳理系统架构，生成 MongoDB 数据操作、后端接口、校验与跳转逻辑，并补充测试和说明文档。在第二阶段，AI 根据新增需求，实现了个人题库、题目去重与复用、分享通知、问卷复制、历史版本查看与恢复、不同版本并存、题库与问卷的共同历史、使用关系查询，以及跨问卷单题统计，并补充相应的自动化测试和浏览器验收。
- AI 做错了什么：最初的删除、发布和关闭确认逻辑存在问题，取消后仍可能执行操作；Windows 下的测试命令也出现过通配符问题。后续扩展中，还出现了共享表单向冻结对象注册失败、两次读取导致题目内容与来源版本可能不一致，以及去重后的来源关系形成初始版本别名环等问题。这些问题随后进行了修复，并通过相应的回归测试或浏览器操作检查。
- 自己改了什么：我调整了交付目录，将程序文件集中到 code/ 中，并检查和修改文档内容。界面提示、保存反馈、题库分页与选题菜单，以及通知提醒等调整，由我在使用过程中提出要求，再由 AI 实施代码修改。对于题库重复项、发布问卷修改、版本关系、题目使用范围和跨问卷统计等问题，我负责检查使用效果、明确预期并提出后续调整要求，不将这些需求反馈记为自己手写实现。
- 自己设计了什么：我根据课程要求确定功能范围、简化架构和分阶段开发安排，并组织代码、文档及测试的交付结构。在第二阶段，我结合使用需求，明确了题目需要重复使用、分享后由接收者选择是否入库、不同问卷可使用不同版本、题库与问卷的历史需要双向同步，以及查看使用范围和汇总统计等要求。具体的数据结构、数据库操作和后端实现由 AI 辅助完成，并通过测试和实际操作检查效果。

具体工具、提示词、生成结果及修改情况见 [AI 使用日志](文档/AI使用日志.md)。对于没有完整保留的历史提示，只记录能够确认的摘要；概念学习、实际代码修改和测试验证也分别说明。
